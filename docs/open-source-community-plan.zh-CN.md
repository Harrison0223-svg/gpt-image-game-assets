## 1. 决策与目标

**主张：持续维护自己的 GPT Image Game Assets，同时在 Pillow 建立深入贡献记录，向 Codex 提供有证据的问题反馈。** ImageIO 是备选，暂不同时铺开多个大型项目。

这个方向最适合现有积累：Python 图像处理、透明度检查、精灵帧与 GIF、Codex 工作流，以及 Windows 下的实际使用与排错。外部贡献反过来提高本项目的可靠性，容易形成连续工作，而非每次寻找陌生项目重新起步。

目标是让其他维护者愿意再次与你协作：解决真实问题、交付容易复核的材料、完成评审返修、对后续回归负责。未来资助或维护者计划的申请，从这些成果中整理证据。

**前三个月的成功标准是建立一个可信的贡献循环，不是获得某个头衔或达到某个 PR 数量。** 重点成果是：本项目可复现使用；至少一条外部问题从复现推进到反馈或修复；在同一外部领域持续跟进；实际状态有公开链接可查。合并由对方维护者决定，不设置强制合并指标。

## 5. 从贡献者走向维护者的路径

| 阶段 | 实际承担的工作 | 可以如实使用的身份 |
| --- | --- | --- |
| 有用的使用者 | 提供最小复现、测试新版本、解释明确的使用问题 | User / Bug reporter |
| 持续贡献者 | 修复、测试、文档被接收；认真处理评审返修 | Contributor |
| 某个领域的固定协作者 | 在相同模块跟进回归、检查他人的补丁、补充版本验证 | Regular contributor / Reviewer，按事实说明 |
| 被信任并获得职责 | 对方明确委派 triage、评审、发布或模块维护，必要时授予权限 | Maintainer / Core maintainer，仅限明确获得的职责 |

**计划目标可以是成为维护者；履历中不能提前把贡献者写成维护者。** Fork 所有权、几个已合并 PR 和维护对方整个仓库不是同一回事。形成稳定贡献关系后，可以询问对方最缺什么帮助；优先接具体职责，不急于索取头衔。

本项目的 Primary maintainer 身份，与在 Pillow、Codex 等项目中的身份分别记录。

## 6. 执行节奏与阶段验收

默认每周约 6 小时，后续按游戏生产安排调整。这是工作预算，不是自动执行日程。同期最多维护 **1 个外部开发分支/PR + 1 个反馈线程**；已有返修优先于新任务。

### 第 1–2 周：建立可复现入口

- 完成本项目 P0 上手与媒体引用核验，记录遇到的真实问题。
- 阅读 Pillow 当前贡献规则，搭建隔离开发环境并完成其自测；构建失败先修复环境，不在环境不明时改上游代码。
- 核验两条 Pillow 候选的最新状态、现有讨论和关联改动，选出一个有新信息的切口。
- 形成第一份可审阅的复现包或文档/测试改动草案。先有实测材料，再发评论或 PR。

验收：他人能重复运行；报告说明当前观察及与旧讨论的差异；没有证据时明确记录“未复现/无需投稿”，不把准备工作写成外部贡献。

### 第 3–6 周：完成协作闭环

- 在已授权的投稿范围内提交一项有用的改进或复现结果，并跟进维护者反馈。
- 对评审意见逐条回复、修改、验证；没有合并也要保留明确的关闭原因和学到的约束。
- 对方需要时测试关联补丁或后续版本，把验证结果回到同一线程。
- 自有项目围绕实际反馈维护；有用户可见改进后发布下一个版本。

验收：至少一个任务走完“问题 → 证据 → 对外协作 → 结论/后续”的过程；提交、接收、合并、随版本发布分别记录。

### 第 7–12 周：建立稳定领域

- 继续在同一图像处理领域贡献，优先补充回归测试、验证其他人的修复、解答自己真正验证过的问题。
- 如果维护者愿意合作，再承担一个明确的小范围常规工作，例如 Windows 复现、GIF 回归验证或某类文档维护。
- 若主线连续几周没有可推进的任务，启动 ImageIO 备选调研，仍保持一个外部开发任务上限。
- 整理一次公开维护回顾：解决了什么、谁受益、哪些没有解决、证据链接是什么。

验收：有跨周持续贡献，而不只是一次 PR；贡献与当前游戏美术工具链相互促进。维护者任命不作为三个月的必达条件。

### 固定周循环

| 时间预算 | 工作 |
| --- | --- |
| 约 40 分钟，分两次 | 查看已有任务的评审、补充信息请求及本项目问题 |
| 约 3 小时 | 一个外部问题的复现、阅读、修复或验证 |
| 约 1.5 小时 | 自有项目的真实反馈、文档与版本维护 |
| 约 50 分钟 | 记录公开证据、复盘、决定下一个最小任务 |

有评审返修时调整分配。外部维护者没有承诺回复时限；按对方规则等待，只在有新证据或合理间隔后做一次有内容的跟进，不连续催促或创建重复 PR。

## 7. 每次外部贡献的交付标准

1. **查重与范围**：阅读近期讨论、已有 PR、贡献指南；明确这次解决谁的什么问题，为什么适合放在上游。
2. **可复现材料**：最少依赖、输入来源与权限、完整命令、准确版本、预期/实际结果；日志去掉凭证和私人路径。
3. **最小改动**：一个任务一个分支，不夹带格式化、无关重构或依赖升级。
4. **验证**：修复先证明问题，再运行受影响测试及仓库规定检查。Pillow 先执行自测；图像/动画相关结果还要检查真实文件，自动通过不能替代视觉判断。
5. **说明与协作**：清楚写出 What/Why/Validation，注明实际 AI 协助；用户能够解释每处关键改动。以目标仓库具体规则为准。
6. **后续负责**：提交后处理评审与回归，最终把已合并提交、关闭理由或版本发布链接补齐。

小型明确文档修复，不统一强加“必须先等维护者审批”；是否先开 Issue 依目标仓库规则。大型功能、设计变化或上游明确要求先讨论的工作，先对齐方向。[S1][S3][S5]

如果任务涉及真实图像素材，新生成/编辑的视觉美术只使用内置 GPT Image；原图、提示词和审阅记录保留。算法测试可使用明确标注的人工测试像素，不能把测试图伪装为游戏美术验收。

| 待产生首项记录 | — | — | — | — | 尚未投稿 | — |

允许的状态：`候选`、`本地复现`、`草案`、`已提交`、`修改中`、`已接收/已合并`、`已随版本发布`、`已关闭（注明原因）`。本地通过测试、维护者表示感谢、PR 合并和发布不是同一个阶段。

未来申请整理成一页材料，优先提供：

- **角色证据**：自己的仓库控制与发布记录；外部项目的实际职责或明确任命。
- **维护证据**：评审、Issue 闭环、回归处理、版本发布及跨周持续性。
- **影响证据**：真实用户反馈、下游公开引用、可核验的使用/下载信息；注明统计时间与口径，不把 clone 当独立用户。
- **代表贡献**：最有解释力的少量实例，写清问题、改进、测试和他人反馈，不罗列几十个低价值链接。
- **支持需求**：预计资源用于哪些具体维护工作，预算与实际记录对应。

GitHub 的贡献图只是一种展示：commit 的关联邮箱、独立仓库与默认分支等条件影响显示。不能为了绿格改写历史、拆分无意义提交，或把仅留在 Fork 的工作说成已经贡献给上游。正确检查归属，保留原作者与必要的协作署名。[S8]

### 申请用途的明确区分

| 机会 | 贡献记录有什么帮助 | 不能从记录直接推出什么 |
| --- | --- | --- |
| Codex for Open Source | 活跃维护、实际职责、生态价值和明确资源用途可以支持陈述；外部贡献可补充协作证据 | 不是积累若干 PR 后自动通过；在别人的项目贡献，不会自动成为其 primary/core maintainer [S9] |
| GitHub Sponsors | 持续成果、公开维护记录与服务对象有助于他人判断是否支持 | 这是接受社区赞助的机制，不是 GitHub 自动发奖金；是否能收款要另核验本人真实居住地区、账户与当时条件 [S10] |
| 外部项目的维护职责 | 在同一模块持续交付并及时处理反馈，能建立信任 | 不保证被任命，也不把自己的计划当作对方的承诺 |

其他厂商支持计划，在确有工具需求时再核验当时规则，按一套证据复用材料；不把未读到的资格、名额或等待周期写成确定条件。

## 9. 执行边界与下一次启动清单

以下规则已在调研日读取；仓库活动通过 GitHub 元数据和近期 PR 抽样检查。`pushed_at` 仅表明有推送，不单独证明社区欢迎新贡献。候选 Issue 在调研时显示 Open，但没有完成本地复现。GitHub 搜索 API 在部分候选检索时触发 secondary rate limit，相关搜索已停止；因此没有把 ImageIO 或 Codex 的未核验搜索结果列为具体可接任务。
